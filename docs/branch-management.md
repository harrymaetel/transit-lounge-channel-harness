# 브랜치와 다중 기기 작업 관리

공용 운영 로그: https://github.com/harrymaetel/transit-lounge-channel-harness/issues/1

## 요청과 브랜치

1. 어느 기기에서든 GitHub의 New issue → `작업 요청 / 외부 기기 인계`로 요청을 남긴다.
2. 작업자는 Issue를 확인하고 담당자와 시작 상태를 기록한다. 중복 작업 여부를 확인한다.
3. 요청 하나에 `feat/<issue>-<slug>`, `fix/<issue>-<slug>`, `chore/<issue>-<slug>` 중 하나의 브랜치를 만든다. main은 통합 기준으로 사용한다.
4. PR에 작업 Issue와 검사 결과를 연결한다. 완료 후 main에 병합하고 병합 여부와 미사용 여부를 확인한 브랜치만 정리한다.

```sh
git fetch origin --prune
git status --short --branch
git switch main
git pull --ff-only origin main
git switch -c feat/123-short-description
```

작업 트리가 깨끗할 때만 위 전환 절차를 실행한다. 같은 브랜치를 여러 기기에서 동시에 수정하지 않는다. 병렬 작업은 다른 Issue와 브랜치로 나눈다. 강제 push나 타인 작업 덮어쓰기로 충돌을 해결하지 않는다.

## 기기를 옮길 때

기존 기기에서 커밋하고 브랜치를 push한 뒤 Issue에 `인계 대기 / 브랜치 / 마지막 SHA / 검사 결과 / 다음 행동`을 기록한다. 새 기기에서는 먼저 fetch하고 해당 원격 브랜치를 추적한다. 기존 추적 브랜치가 있다면 전환 후 `git pull --ff-only`한다. 미커밋 파일은 GitHub로 동기화되지 않는다.

GitHub 웹 편집·외부 에이전트도 같은 규칙을 따른다. 로컬 폴더나 이 채팅의 기억만으로 다른 기기의 상태를 판단하지 않는다.

## 자동 로그의 범위

`operations-log.yml`은 push, 브랜치/태그 생성·삭제, Issue 접수·종료·재개·담당 변경, PR 생성·갱신·병합·종료를 운영 로그 Issue에 기록한다. UTC 기록 시각, 작업자, 참조, SHA, 대상과 실행 링크만 저장한다. 대화 원문과 커밋 메시지는 복사하지 않는다. main에 설정이 반영된 이후의 이벤트부터 대상이다.

GitHub Actions가 꺼져 있거나 권한·서비스 오류가 있으면 자동 기록이 실패할 수 있다. Actions 실행 상태와 실제 GitHub 이력을 함께 확인한다. GitHub의 제한에 따라 일부 대량 ref 생성/삭제 이벤트와 다른 워크플로의 GITHUB_TOKEN이 만든 이벤트는 발생하지 않을 수 있다. 각 작업의 Issue/PR이 상세 기록의 기준이다. 외부 fork에서만 발생한 push는 이 저장소 로그에 남지 않으며 PR로 연결해야 한다.

이 자동화는 요청을 실행하거나 브랜치를 병합·삭제하지 않는다. 외부 요청 접수는 작업 대기 상태이며, 실행 중인 에이전트가 확인하거나 사용자가 이 대화에서 처리를 요청해야 작업이 시작된다.

## 이 대화에서 이력 확인

`외부 기기 작업 현황 보여줘`, `지난 작업 이력 정리해줘`, `Issue #번호 이어서 진행해줘`라고 요청한다. 에이전트는 실제 원격 브랜치, 열린 PR/Issue, 운영 로그와 CI를 조회하고 이 대화에 확인 시각(KST), 변경 사항, 처리 결과, 관련 링크, 다음 행동을 요약한다.

GitHub에서 발생한 이벤트가 이 채팅에 자동으로 새 메시지를 보내지는 않는다. 별도 주기 감시나 알림은 설정하지 않았다. 이전 대화 전체를 공개 저장소에 복사하지 않는다. 기존 `harness/decision-log.jsonl`은 브랜드·사용자 결정 기록용이며 Git 운영 이벤트와 구분한다.
